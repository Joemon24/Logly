# Ubuntu v2 verification procedure

Status: live Ubuntu validation is pending. Run on an isolated Ubuntu host with a dedicated Kafka topic/group and disposable agent state. The existing Compose detector defaults to v1; start a separate Python consumer with the v2 topic, distinct group and trusted Elasticsearch endpoint.

1. Install Go 1.23+, build with `cd agent && go build -o ../bin/logly-agent-v2 ./cmd/agent-v2` and provision a dedicated service account. Install the binary and review the example v2 unit and environment below. The account needs read-only access to the chosen logs and ownership of its SQLite state directory. Confirm `sudo -u logly test -r /var/log/auth.log` before starting. Do not change permissions on live logs merely to make a check pass.
2. If rsyslog writes the file, set `LOGLY_V2_LOG_PATH` to it. Start with the audit path unset. Install the service template, run `systemd-analyze verify`, then check `systemctl status logly-agent-v2` and `journalctl -u logly-agent-v2`. Confirm source availability and outbox counters. Exercise legitimate test SSH and sudo activity on the staging host and verify category, outcome and agent ID in Events.
3. For optional audit collection, first arrange a narrowly scoped execution audit rule for a known benign program and write/attribute watches for the intended test files. The supported operator-defined keys are `logly-exec`, `logly-passwd` and `logly-group`. The last two mean `/etc/passwd` and `/etc/group` respectively. Use the distribution’s standard audit rules configuration and verify keys with `auditctl -l`. Confirm the service account can read the audit log using a scoped ACL or the host’s approved log group. Never run the agent as root to read the log. Set `LOGLY_V2_AUDIT_PATH`, restart, and check benign execution and watched-file activity recorded in a disposable VM under an approved procedure. Check that command arguments and unrelated audit records are not indexed.
4. Rotate a staging copy of the log under rename-and-create logrotate, exercising input immediately before and after rotation. Verify the checkpoint generation changes and no accepted event is duplicated. Repeat across a service restart and inspect reported coverage gaps for an unavailable rotated file. Test copytruncate separately and record its loss window.
5. Stop the staging broker, append a benign fixture batch, confirm the durable outbox grows up to its configured limit, and check that additional accepted records remain at the source checkpoint. Restart the agent during the outage, then restore the broker and verify the same event IDs are delivered and offsets advance only after Elasticsearch/analysis succeeds. Confirm graceful shutdown leaves unacknowledged rows available on restart.
6. Record Ubuntu and package versions, rules, commands, expected/observed counts and any permission or coverage gaps. Keep Kafka and Elasticsearch isolated and retain logs long enough to compare behavior across restarts.

Use `deploy/logly-agent-v2.service` and `deploy/logly-agent-v2.env.example` as staging templates. The existing v1 templates still apply to the legacy agent.
